请求 R 归 DP1；⑥⑦仅周期触发，非每个请求都重排。
独立情景 R / Q；仅展开 R 的 E0 分支。 教学配置：TP=1 · DP=2 · EP=2 · 同两张 GPU
请求 / 控制 激活 / 结果 权重 / 映射 统计反馈
  1. 客户端交付 R → API 进程内的 DPLB 接手。
  2. 队列统计 → 本地选 rank → R 交给 DP1 的 EngineCore。
  3. R 的队列与 KV 在 DP1；本批 t0 的激活进入 MoE。
  4. router 选逻辑 E0 → 当前映射选物理 p0 → t0 激活去 GPU0。
  5. GPU0 的 E0 算完 → t0 结果回 DP1 → 继续后续层与采样。
  6. 各 rank 记录专家命中 → 到重排周期汇总 → 各 rank 计算新放置。
  7. 本次周期重排：搬好专家权重 → 更新映射 → 后续 token 使用新位置。
  8. 本步输出 → API → 客户端；未结束的请求留在 DP1 继续生成。

  3. 第 1 步：prefill 与采样完成：用旧布局；每个请求 1 个 token、各选 2 个专家 → 命中 [3,1,1,1]。计数 1<4，直接返回本步结果。
  4. 第 2 步：同一批请求继续 decode：累计命中 [6,2,2,2]；计数 2<4，继续使用旧专家布局。
  5. 第 3 步：E0 已经很热，但还不到期：本周期新增合计 [9,3,3,3]；E0 占一半命中。计数 3<4，不触发重排。
  6. 第 4 步：先完成 forward 与采样：仍按旧映射计算；本步新增 [3,1,1,1]。请求尚未结束，本步输出也尚未返回。
  7. 步后检查：4≥4，触发重排：先更新统计窗口，再把计数 3→4；达到 step_interval 后重置为 0，进入重排。
  8. 汇总负载，决定新的副本和位置：物理计数→逻辑专家→EP all-reduce，得到 [12,4,4,4]；E0 从 1 份增为 3 份，生成目标布局。
  9. 本地来源先存入临时缓冲：GPU0：旧 p2→缓冲 p1、旧 p0→缓冲 p2；GPU1：旧 p3→缓冲 p4。在用权重仍不改。
  10. 跨卡传 E0、E1 权重：GPU0 的 p0/E0→GPU1 缓冲 p5；p1/E1→GPU1 缓冲 p3。A/B/C 仍处于同一请求中。
  11. 等待全部发送和接收完成：GPU1 缓冲 [E1,E3,E0] 就绪；下一次 forward 仍要等写回和映射切换。
  12. 把缓冲写回目标物理槽：p0 保留，其余槽写入目标权重；此刻旧映射还未切换，不启动下一步 forward。
  13. 所有层完成后，切换映射：更新 physical↔logical 和副本数。新布局生效；请求、DP 归属、KV cache 均未搬动。
  14. 返回第 4 步输出，请求仍未结束：EPLB 返回后构造本步输出；Scheduler 更新 A/B/C，准备下一次 decode。
  15. 第 5 步：同一请求使用新专家布局：A/B 仍在 DP0，C 仍在 DP1；token 的专家计算按新映射找物理副本。
  16. 请求结束是另一个事件：第 5 步的 EPLB 计数为 1，不再重排；示例输出 EOS，Scheduler 才结束 A/B/C。专家迁移已提前完成。

DPLB 选组与 EPLB 放置：边界及源码
  • DPLB 选择一个 DP rank 对应的 EngineCore；若 TP>1，它背后是一组 TP workers。本例 TP=1，每个 DP rank 对应一张 GPU。
  • 此处单 API client：从 DP0 开始扫描，分配后本地 waiting 加 1。一般情况起点为 floor(DP 数 × client_index / client_count)，分配后加 client_count。同分保留扫描时先遇到者；起点不会逐请求轮转。
  • 此图的三个新请求之间不接收新统计；Coordinator 后续会用新快照覆盖本地估计。4 是此版的固定启发式权重，不代表等待请求一定耗时 4 倍。分值不直接使用 token 数、KV 命中或 GPU 利用率。显式指定 data_parallel_rank 会绕过该打分路径。
  • EPLB 策略从每逻辑专家一个副本开始重算，总物理槽固定。放置算法输入没有旧映射，因此目标是负载均衡，不保证迁移量最小。
  • 单节点、4 个逻辑专家、6 个物理槽，每 GPU 必须放 3 个副本。等权副本按 q0…q5 展示；源码排序不保证等权元素顺序，最终槽位可不同。GPU 累计负载并列时，先取较小 rank。
  • 多节点且专家组数可被节点数整除：先把专家组分给节点，再在节点内复制、放置到 GPU；否则进入全局策略。本图固定单节点。
  • 权重迁移先保留不变槽、本地复制到缓冲、P2P 发送/接收并等待、缓冲写回；所有层重排完成后更新映射，再进入后续 forward。API 可继续接收排队请求。
  • 同一逻辑专家的远端接收按 rank 去重；收到一次后可复制到本卡多个目标槽。多个旧持有 rank 时，远端目标分摊给旧持有者。
  • 数据为教学输入；执行的是规则仿真，未运行模型或测量加速效果。EPLB 装箱使用每副本平均负载估计。

示例配置、触发边界与源码
  • 固定单节点、DP=2、TP=PP=1、EP 跨两张 GPU，已启用 EPLB。A/B 归 DP0，C 归 DP1；每请求每步贡献一个 token，MoE top-2。A 命中 E0/E1，B 命中 E0/E2，C 命中 E0/E3；每步合计 [3,1,1,1]，4 步为 [12,4,4,4]。
  • 教学配置 window_size=4、step_interval=4，计数从一次正常重排后 0 开始。前 3 步仅显示本周期新增统计，旧窗口样本省略；第 4 步已用新 4 步完全覆盖窗口。旧布局是运行中示例快照，不是默认启动布局。默认参数为 window_size=1000、step_interval=3000；启动计数设为 interval−floor(interval/4)，所以首次重排较早。
  • 触发周期重排的条件：本次 EPLB 计数加 1 后 ≥ step_interval。专家负载决定副本和位置；源码没有“某专家命中 N 次”或 balancedness 日志阈值的触发分支。即使负载均匀，到期也重新规划；新旧槽位一致时保留权重。
  • 窗口统计的是 token 的 top-k 专家选择次数，不是用户请求数；图中汇总值用于讲解。运行时先记各 rank 的物理专家计数，到期才按逻辑专家归并并在 EP 组 all-reduce。
  • 启动时加载权重、创建映射和统计窗口，profiling 预留通信资源。本次迁移的临时权重缓冲在重排时申请并跨层复用；不是每个请求到达前先迁移一次。
  • 本版常见生成路径是 forward→logits/采样→bookkeeping→EPLB→返回本步输出。迁移可插在同一请求的两个 decode 步之间；权重搬完、所有层映射更新之后才进入后续 forward。图中时间间距不表示耗时。
  • 请求的 DP 归属和 KV cache 不变。这里显示专家权重的 P2P，forward 内 token activation 的 EP 派发/回收另属计算通信。API 可继续接收排队请求。
  • 在线 DP dummy 步不写入负载窗口，但仍推进重排计数，使空闲 rank 也参加同步重排。此例两 rank 每步均有真实 token；不展开 dummy 分支。
  • E0 依次取得两个冗余副本：12÷1→12÷2→12÷3；随后六份预测负载均为 4。采用前图相同的合法并列顺序，目标 [E0,E2,E0 | E1,E3,E0]；等权排序不同可产生其他槽位排列。
  • 请求结束仅作教学收尾，示例令第 5 步输出 EOS。此图为源码规则仿真，未运行模型或测量迁移性能。
