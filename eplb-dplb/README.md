## 五章流程

| 章节 | 内容 |
| --- | --- |
| 1 · 两层协作总览 | DPLB 分配请求；MoE token 经 dispatch、专家计算和 combine 回到请求所属 DP；EPLB 按周期调整专家。 |
| 2 · DPLB 统计反馈与请求 | Scheduler 队列计数 → Coordinator → API client → 新请求打分、发送与本地估计更新。 |
| 3 · DPLB 为什么选这个 DP | 对比三个队列情景，逐个追踪 R1–R3 的选择和分值变化。 |
| 4 · EPLB 副本分配与放置 | 根据负载 `[12,4,4,4]` 给 E0 增加两个副本，再把六份专家装入两张 GPU。 |
| 5 · 请求时间线与权重迁移 | A/B/C 跨多个模型步继续执行；到期后本地复制、P2P 传输、缓冲写回、映射切换，再返回本步输出。 |

前两章跟踪请求 R，第 3 章使用独立的 R1–R3 连发情景；第 4、5 章共享 EPLB 负载与目标布局。不同情景的请求和队列状态不自动承接。

## 三个 DPLB 情景

本例单 API client 从 DP0 开始扫描，选择 `score = 4 × waiting + running` 最小的 DP rank。每次发送后，本地 waiting 先加 1；三个新请求之间没有新统计到达。

| 情景 | 初始 DP0：等待 / 运行 / 分值 | 初始 DP1：等待 / 运行 / 分值 | R1 的选择 |
| --- | --- | --- | --- |
| 原例 | 2 / 4 / 12 | 1 / 2 / 6 | DP1 |
| 请求更少的反例 | 2 / 0 / 8 | 0 / 5 / 5 | DP1；DP0 请求总数更少，但分值更高 |
| 同分 | 1 / 0 / 4 | 0 / 4 / 4 | DP0；平分保留扫描中先遇到者 |

一般情况下，扫描起点由 `client_index` 和 `client_count` 决定，分配后本地 waiting 增加 `client_count`。起点不会逐请求轮转，后续 Coordinator 快照会覆盖本地估计；分值不直接使用 token 数、KV 命中或 GPU 利用率。

## 源码基线与教学边界

基线固定为 [vLLM v0.11.0](https://github.com/vllm-project/vllm/tree/v0.11.0)，展示该版本的**同步 EPLB 路径**。源码定位见页面中的展开说明。

- 固定单节点、DP=2、TP=PP=1，EP 跨同两张 GPU。DPLB 选择 DP rank 对应的 EngineCore；专家执行位置不改变请求、Scheduler 或 KV cache 的归属。
- EPLB 示例有四个逻辑专家和六个物理槽，旧布局为运行中快照 `[0,1,2 | 3,2,3]`，目标为 `[0,2,0 | 1,3,0]`。等权副本采用一组合法的教学顺序，源码排序不保证唯一槽位排列；每副本负载是规划估计。
- 时间线使用 `window_size=4`、`step_interval=4`，从一次正常重排后的计数 0 开始。A/B 归 DP0、C 归 DP1，每请求每步一个 token、top-2，每步专家命中合计 `[3,1,1,1]`。默认参数为窗口 1000、间隔 3000；启动计数并非从 0 开始。
- 步数决定何时重排，专家负载决定如何放置。同步重排发生在本步 forward、采样之后，先完成权重传输与所有层写回，再更新映射、返回本步输出；同一请求可在下一步继续生成，无须等到请求结束。
- forward 中的 token 激活 dispatch/combine 与重排中的专家权重 P2P 是不同通信。在线 DP dummy 步不写入负载窗口，但仍推进重排计数并参与同步；API 仍可接收排队请求。
- 页面展示源码规则与教学数据，未运行 vLLM 模型或测量性能；图中间距和步骤数量不代表耗时或加速效果。

### 深入调用链的阅读边界

DPLB 的计数读取、统计快照、后台订阅任务与请求发送分别展开；后台 `create_task()` 是任务创建关系，统计覆盖不是请求选择函数的同步子调用。EPLB 沿真实的专家规划与迁移调用继续展开接收方配对，并把通信等待、缓冲写回和最终映射切换分开。

子调用复用原图中对应阶段的入口；没有独立快照时，节点注明只定位所属阶段。调用编号可随展开调整，原节点 ID 保持稳定；源码证据的调用点与实现均以场景声明的完整 commit 为准。
